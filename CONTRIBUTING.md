# Вклад в развитие sysflex

Спасибо за интерес к проекту! Мы рады любому вкладу: исправлениям багов,
новым функциям, улучшению документации, новым плагинам и темам оформления.

## Быстрый старт для разработки

Через `make` (нужен только компилятор):

```bash
git clone https://github.com/fanxcz/sysflex.git
cd sysflex
make test      # собрать и запустить модульные тесты
make debug     # сборка с AddressSanitizer/UBSan + тесты
```

Через CMake:

```bash
git clone https://github.com/fanxcz/sysflex.git
cd sysflex
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DSYSFLEX_WERROR=ON
cmake --build build -j"$(nproc)"
(cd build && ctest --output-on-failure)
```

Дымовые тесты самого бинарного файла (все режимы запускаются по-настоящему):

```bash
cmake -S . -B build -DSYSFLEX_BUILD_SMOKE_TESTS=ON
cmake --build build -j"$(nproc)"
(cd build && ctest --output-on-failure)
```


## Требования к коду

- Стандарт **C++17**, без добавления внешних зависимостей (кроме pthread).
- Компиляция без предупреждений при `-Wall -Wextra`; в CI дополнительно
  включён `-Werror` (`-DSYSFLEX_WERROR=ON`).
- Комментарии к нетривиальной логике пишем на русском языке.
- Одна функция — одна ответственность. Методы `SystemMonitor` не должны
  зависеть друг от друга по порядку вызова.
- Не используйте `system()`/`popen()` там, где можно прочитать `/proc` или
  `/sys` напрямую — это быстрее и надёжнее. Один `popen` — это `fork+exec`
  ценой порядка миллисекунды, а `update()` вызывается каждую секунду.
- Данные, которые всё же требуют внешней утилиты, добавляйте в «медленный»
  набор: метод `collectXxx()` вызывается из `refreshSlowCache()` и
  кэшируется в `SystemMonitor::slow_`. Так новый источник не замедлит
  каждый кадр живого режима.
- Содержимое `/proc` и `/sys` читаем без доверия: вместо `std::stol`/
  `std::stoul` используйте `utils::toLong`/`utils::toULong`, которые не
  бросают исключений. Необработанное исключение — это падение sysflex.
- Вывод в JSON формируйте через `utils::jsonEscape` (строки) и
  `utils::jsonNumber` (числа) — только так документ остаётся валидным
  при `NaN`/`Inf` и некорректном UTF-8.
- Новый функционал обязательно сопровождается тестом в `tests/test_main.cpp`,
  если он поддаётся модульному тестированию (utils, sparkline, config,
  themes, display и т.д.).
- Изменили поведение или добавили опцию — обновите `--help` в
  `include/sysflex/config.hpp`, `man/sysflex.1` и `README.md`.

## Версионирование

Версия объявляется в **одном** месте — константа `VERSION` в
`include/sysflex/config.hpp`. CMake сравнивает её с `project(... VERSION ...)`
и падает на этапе конфигурации при расхождении; `Makefile` читает её из того
же заголовка. При подготовке релиза обновите оба места и добавьте запись
в `CHANGELOG.md`.

## Как добавить новую тему оформления

1. Откройте `include/sysflex/themes.hpp`.
2. Добавьте новую запись в `allThemes()` с ANSI-кодами (256-цветная палитра
   `\033[38;5;NNNm` предпочтительнее 16-цветной для лучшей консистентности).
3. Обновите таблицу тем в `README.md` и список в `man/sysflex.1`.

Тема подхватится в `--list-themes` и в проверке `--theme` автоматически.

## Как добавить новый плагин

Плагины — это обычные исполняемые скрипты (bash, python, что угодно) в
каталоге `plugins/`. sysflex просто запускает все исполняемые файлы из
этого каталога и выводит их stdout. Смотрите `plugins/uptime.sh` как
минимальный пример.

1. Создайте скрипт в `plugins/your_plugin.sh`.
2. Сделайте его исполняемым: `chmod +x plugins/your_plugin.sh`.
3. Скрипт должен быстро завершаться (в идеале — до 1 секунды) и выводить
   только полезную информацию в stdout.
4. Скрипт обязан проходить `shellcheck` — CI это проверяет.
5. Если скрипт обращается в сеть, ставьте таймаут (`curl -m 2`) и
   завершайтесь с кодом 0 при недоступности сервиса: пустой вывод sysflex
   воспринимает как «плагин пропущен».

## Процесс Pull Request

1. Форкните репозиторий и создайте ветку от `main`: `git checkout -b feature/my-feature`.
2. Внесите изменения, убедитесь, что `make test` (или `ctest`) проходит без ошибок.
3. Обновите `CHANGELOG.md` в разделе `[Unreleased]`.
4. Не коммитьте артефакты сборки: бинарник `sysflex`, `build/`, `*.o`
   уже перечислены в `.gitignore`.
5. Откройте Pull Request с понятным описанием: что изменилось и зачем.
6. Дождитесь прохождения CI (GitHub Actions) — PR с падающим CI не мержится.

CI прогоняет матрицу **GCC/Clang × Release/Debug** с `-Werror`, модульные
тесты, дымовые тесты всех режимов, проверку валидности JSON штатным парсером
Python, сборку через `Makefile` (без CMake) и `shellcheck` для скриптов.

## Сообщения о багах

Открывайте issue с указанием:
- дистрибутива и версии ядра (`uname -a`);
- команды, которая вызвала проблему;
- полного вывода ошибки (если есть);
- вывода `sysflex --once --json` — он помогает понять, какие поля
  не заполнились на вашей системе.
